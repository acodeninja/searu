# xss — confirm cross-site scripting in a real browser (T1595, CWE-79)

Prove XSS the way it actually fires: a headless browser renders the app with a payload injected, and a
payload that *executes* raises a marked dialog — the reliable signal for **DOM-based** XSS that dalfox's
raw HTTP requests cannot see. Reconnaissance/Initial-access, Active tier — allow-list T1595; no
authoriser needed. Complements dalfox (fast, reflected) — reach for `xss` on JS-rendered sinks.

Run — mark the injection point with `PAYLOAD` in the target (a query value or a hash route), or name a
query param:

    searu run xss --technique T1595 --target 'http://host:port/#/search?q=PAYLOAD'
    searu run xss --technique T1595 --target 'http://host:port/#/track-result?id=PAYLOAD'
    searu run xss --technique T1595 --target http://host:port/search -- --param q

Read results:

    searu findings --tool xss     # a confirmed CWE-79 finding naming the payload and the url that fired

A confirmed hit means client-side code executed. Escalate within the ROE (steal the session/JWT, act as
the victim) or report it as client-side code execution. Don't paste raw browser output. See
`searu tool advice xss`.
